Testing#

rocm-ernic ships with several test programs and a CTest integration that can be run from the build directory.

Test Programs#

test_pci_client#

A vfio-user client that connects to the server and performs basic PCI configuration space queries:

  • Socket connection to server

  • PCI Vendor ID verification (Pensando: 0x1dd8)

  • PCI Device ID verification (ROCm ERNIC: 0x1002)

  • PCI subsystem verification (ROCm ERNIC: 0x1dd8:0x5400)

  • PCI Class Code verification (Network Controller)

  • PCI Header Type verification (Type 0)

  • BAR register reads

  • Interrupt configuration reads

Exit codes: 0 = pass, 1 = failure.

test_data_transfer#

Comprehensive RDMA data transfer test using libibverbs:

  • RDMA device discovery and opening

  • Protection Domain allocation

  • Completion Queue creation

  • Queue Pair creation and state transitions

  • Memory Region registration

  • Send / recv operations with varying buffer sizes (64 to 4096 bytes)

Requires an RDMA device (via the guest ionic_rdma driver or real hardware). Exits 77, skipped, if it finds no device, or if creating a QP on the one it found fails.

find-rdma-device-tuple#

A shell test registered with CTest. It uses a synthetic sysfs tree to verify RDMA discovery requires the emulated vendor/device/subsystem tuple and rejects near matches.

find-ipv4-gid-index#

A shell test registered with CTest. It uses synthetic sysfs GID tables to verify scripts/find-ipv4-gid-index.sh finds an address’s IPv4-mapped GID at any index and rejects malformed arguments.

test_rdma_cm#

RDMA Connection Manager test using libibverbs. Validates connection setup and teardown paths.

test_ionic_ci.sh#

Shell test for the ionic emulation path, registered with CTest as ionic-ci. It needs no VM and no RDMA device:

  • Server starts on the loopback and none backends, and with no extra flags at all

  • PCI identity is 0x1dd8:0x1002

  • BAR geometry is 64 KB BAR0 (32 KB register window) and 4 MB BAR2, with 32 MSI-X vectors under compat and 97 under generic-400g

  • Clean shutdown on SIGTERM

  • The stats file carries the full counter set

  • --tap attaches to an existing host TAP

The last check is skipped unless ERNIC_TEST_TAP names a TAP interface owned by the current user, since creating one needs CAP_NET_ADMIN:

sudo ip tuntap add dev ernic-ci0 mode tap user "$USER"
ERNIC_TEST_TAP=ernic-ci0 ctest --test-dir build -R ionic-ci

In-process ionic device harness#

ernic-test-ionic-harness runs the whole emulated device inside the test process. It links every source the server is built from except rocm_ernic_server.c and ernic_socket.c, builds the device with ionic_device_create() as the server does, and replaces libvfio-user with tests/fake_vfu.c, which keeps guest memory in heap buffers and counts interrupts instead of delivering them. tests/ionic_harness.c then plays the guest driver: devcmds through BAR0, doorbells through BAR2, and rings, work requests and completions in guest memory. It needs no VM, socket or RDMA device, so it runs in every CI build leg, sanitizers included.

Each group of checks is its own CTest test:

  • ionic-harness-devcmds, -bringup: the devcmds, the Ethernet admin queue, the RDMA bootstrap, and MSI-X masking

  • ionic-harness-rdma-reset, -rdma-reset-faults, -rdma-reset-frees: RDMA_RESET_LIF, with a doorbell before the next admin queue exists, the --inject faults still firing after it, and everything the driver made freed, so a region from before it can’t be written

  • ionic-harness-admin: admin commands the device must refuse; -admin-dma, -dp-dma and -eth-dma refuse one DMA at a time in the admin queue, the data path and Ethernet

  • ionic-harness-rc, -atomic, -cq-events: sends, RDMA reads and writes, atomics and fast registration between two RC QPs on the loopback backend, and CQ arming

  • ionic-harness-spec-sge: the same, with work requests laid out behind a speculative SGE length table, as the driver posts them, and the list formats the device must refuse

  • ionic-harness-wrap: send lengths and memory regions whose sums or ends carry past 2^32 or 2^64, which the device must refuse rather than wrap

  • ionic-harness-mr-keys: only the key an MR is bound under reaches it, through fast registration’s rotations, LOCAL_INV and DESTROY_MR

  • ionic-harness-tables, -limits: the EQ, admin queue and MR tables filled, and the counts the LIF identity promises held by every backend’s tables, to the last CQ and QP id

  • ionic-harness-qp-flush, -qp-flush-srq: the flush completions a QP entering the Error state owes its outstanding work requests

  • ionic-harness-ud, -srq: datagrams, address handles and shared receive queues; -srq-rq-ring and -srq-cq-ring post to an SRQ with each of the provider’s two doorbell forms

  • ionic-harness-eth, -eth-rx-sg: Ethernet transmit and receive, and a received frame scattered across a receive descriptor’s SG list

  • ionic-harness-nvmeof: the IB CM handshake on GSI, then a Fabrics Connect and an Identify on the RC QP it binds; -nvmeof-queues refuses more queues than the MR table can serve

  • ionic-harness-s3: the S3 store’s RDMA GET and PUT; this and -nvmeof check that each target refuses key 0

  • ionic-harness-device-reset, -nvmeof, -s3, -p4: a device reset frees everything the guest set up, writes nothing to guest memory, and leaves a device the driver can bring up again; -cmd checks the same of the driver’s RESET device command

  • ionic-harness-lif-reset: what LIF_RESET takes

  • ionic-harness-bus-master: with Bus Master Enable clear the device does no DMA and raises no interrupt, and once it is set it does what it held, once; -d3hot checks the same of D3hot, with BME set

  • ionic-harness-backend-names, -none, -loopback-pair, -mesh-none: which --backend strings name which backend, a QP’s life on the none backend, the loopback backend pairing QPs that name no destination, and that only the tcp backend has a mesh

  • ionic-harness-teardown: a tcp device torn down with resources still allocated frees them all

  • With ERNIC_BUILD_P4, the P4 engine: ionic-harness-p4-port and -p4-attach put it on the Ethernet path and attach it at each guest scope; -p4-rdma, -fp8-map, -fp8-overlap, -p4-cvt, -p4-cvt-map, -p4-drop-map and -p4-deny run compiled programs on RDMA work requests; -p4-devcmd and -p4-devcmd-errors drive the guest’s command surface; and -p4-log-limit checks that what a guest can make the engine log is rate-limited

ctest --test-dir build -R ionic-harness

To run one group directly, pass its name, for example build/tests/ernic-test-ionic-harness rc. Setting ERNIC_FAKE_VFU_LOG_LEVEL to a syslog level (7 for everything) prints the device’s vfu_log() messages.

Driving a server from Python#

tests/py/ stands in for a guest VM. Where the harness above replaces libvfio-user, these suites keep it: they speak the vfio-user protocol to a real rocm-ernic process over its Unix socket, as a VMM does. Guest memory is a memfd that the client mmaps and hands to the server in a DMA_MAP, so the server maps the same pages and the real DMA path runs. Nothing here needs a VM, RDMA hardware, root, or any package outside the standard library.

The modules under tests/py/ernic/ are:

  • vfu.py – the vfio-user client and GuestMemory

  • server.py – starting server processes, holding them to a shutdown deadline, and counting the descriptors they hold

  • ionic.py – the ionic driver, the Python counterpart of tests/ionic_harness.c

  • mesh.py – the TCP mesh wire protocol, a fake manager, and a fixture that starts a manager and some workers

  • pci.py – the config-space register offsets and fields from linux/pci_regs.h, which ernic-pci-regs (tests/pci_regs_dump.c) prints from the header rather than the tests keeping a copy, and the registers a reset puts back

  • check.py – the small test runner the suites report through

Eight suites are registered with CTest:

  • ernic-vfu-client: version negotiation, device and region info, PCI configuration space, BAR access, DMA mapping, interrupts, Bus Master Enable and D3hot each stopping and resuming the device’s writes, the power states it doesn’t support, a function-level reset, a reset and a reconnect each returning the device and the configuration registers a driver writes to their initial state – and the offsets, counts, addresses and vector ranges a client must not get away with

  • ernic-cmb: the Controller Memory Buffer, BAR 4, with --cmb and without – what DISCOVER_CMB and Q_IDENTIFY report, a QP with its send ring in it, the file the client maps it from, whose size can’t change, that a device reset, RESET and a client’s going each clear it, and that a client that went can’t reach the next one’s

  • ernic-ionic-driver: bring-up, connected queue pairs, memory regions whose pages are deliberately out of order, sends with several SGEs or an inline payload, RDMA reads and writes, shared receive queues, the keys and lengths that must fail, and a device reset and a function-level reset that each stop a QP from before them

  • ernic-ionic-hw-stats: the hardware statistics behind a guest’s hw_counters – the STATS_HDRS, STATS_VALS, QP_STATS_HDRS and QP_STATS_VALS tables, that they describe themselves the way the driver reads them, that a buffer too small for the table gets whole entries only, that values for a QP that does not exist are refused rather than zero-filled, and that the --stats-file the exporter reads carries the same numbers. It drives a SEND, an RDMA WRITE and an RDMA READ of three distinct sizes, and checks that every counter in both tables moves by exactly the right amount on the right QP. The structural checks read whatever set the device advertises, so a counter added to either table is covered without touching the test

  • ernic-mesh-stress: a three-node mesh under traffic between every pair of nodes, peers that send frames no real node sends, the protocol version gate in both directions, and nodes killed and restarted while the manager’s descriptors are counted; then, on a second mesh with a 1 s health-check interval, a worker and then the manager paused past the health check, after which the workers have to register again under their own ids

  • ernic-mesh-flow: a three-node mesh pushed past what a node queues from its peers. Two nodes write to each other flat out, each with its queue plugged by the other’s SENDs to a QP with no receive posted, so both hold the other back at once, and neither may stall or give up on the other; then a node READs 120 MiB from a peer at once while the peer plugs its queue, and every READ must complete, with none of the peer’s replies dropped; then a peer floods a node with SENDs that find no receive, and must be slowed rather than cut off, while the node holds no more than its limit and another node’s SEND gets through

  • ernic-mesh-flr: a two-node mesh whose guests pass traffic, then a function-level reset on the worker and then on the manager. The peer’s QP from before the reset must be refused, with its RDMA WRITE kept out of the memory the reset gave back; the peer then makes a new QP, the reset node’s driver loads and makes its QP and region again, and the two connect and pass traffic both ways. The reset node must keep its place in the mesh: no new registration, the same node id, and no dropped connection

  • ernic-p4-driver, built with ERNIC_BUILD_P4: the P4 engine on the live device, with guest frames taken out of the Ethernet transmit ring, through the pipeline, and out the far side (see P4 Match-Action Engine)

ctest --test-dir build -R '^ernic-(vfu|cmb|ionic|mesh|p4)'

To run one directly, and to vary the mesh:

python3 -I tests/py/test_mesh_stress.py \
    --server build/rocm-ernic --size 5

test_vfu_client.py, test_ionic_driver.py and test_mesh_flr.py also need the program that prints the config-space values, --pci-regs build/tests/ernic-pci-regs.

Like the shell suites, they run the server under the command in ERNIC_TEST_SERVER_WRAPPER, so CI’s valgrind leg covers them too.

Two devices in one process#

ernic-test-gsi-mesh (CTest gsi-mesh) builds the same harness twice: one device as the mesh manager and one as a worker, joined over loopback TCP by the real TCP backend. It checks that the two register, that a GID claimed after the mesh has formed is advertised and resolves to the claiming node from the other side, and that neither node resolves its peer’s address to itself. It then sends a CM-shaped MAD on QP1 and checks both that it reaches the peer’s QP1 rather than coming back round, and that it arrives behind the right header: the two nodes’ GIDs are v4-mapped, so a forwarded datagram has to look like RoCEv2 over IPv4, flagged as such, with the sender’s address as its source. Forwarding the MAD correctly and describing it wrongly looks identical from every other angle, and is what used to strand rdma_cm.

It also checks that an address handle finds its destination’s node when it sends, not when it was made. A MAD through an AH whose address no node owns yet is dropped rather than delivered to the sender’s own QP1, and once the worker claims the address the same AH reaches it. So does an AH made before the worker restarts under a new node id. A MAD through an AH the device doesn’t know, or one with no address, is dropped too.

That is the path rdma_cm depends on and the one ERNIC_TCP_GUEST_GIDS cannot cover: it is read once at startup, and one environment variable cannot describe two devices in one process. test_ud_mesh covers the same journey for a UD datagram, but needs two VMs and two real devices, so it cannot run in CI.

ctest --test-dir build -R gsi-mesh

ERNIC_TEST_MESH_PORT moves the port it listens on, for a runner that already has something on the default.

NVMe-oF tests#

Four tests cover the in-process NVMe-oF controller without needing a VM: nvmeof-target-unit (capsule handling and the command sets, block and Key Value), nvmeof-kv-compact-unit (compacting the Key Value store), nvmeof-cm-unit (the IB CM state machine) and nvmeof-ci (a shell test that starts the real server once per documented option spelling and checks what it reports, including that bad options are refused).

ctest --test-dir build -R nvmeof

The guest-side connect needs a VM. It lives in ansible/playbooks/nvmeof-tests.yml, which the hosted system-test-nvmeof job runs end to end, and the Key Value namespace’s in ansible/playbooks/nvmeof-kv-tests.yml, which system-test-nvmeof-kv runs against a controller with a block and a Key Value namespace. See NVMe-oF Controller.

S3-over-RDMA tests#

Five tests cover the in-process object store without needing a VM: s3-token-unit (the RDMA token wire format), s3-http-unit (the HTTP/1.1 subset), s3-target-unit (the store and its transfers against fake DMA ops), s3-tcp-unit (the in-band ARP/ICMP/TCP stack over a loopback) and s3-ci (a shell test that starts the real server once per documented option spelling).

ctest --test-dir build -R '^s3-'

The guest-side transfer needs a VM, because it needs a real ibv_reg_mr for the token to describe. tests/s3_rdma_client.c is built and run inside the guest by ansible/playbooks/s3-tests.yml, which the hosted system-test-s3 job runs end to end. See S3 over RDMA Object Store.

Running Tests#

Quick Local Test#

./scripts/run-local-tests.sh

This script needs a build in build/. It starts the server, runs test_pci_client against it, and cleans up.

Manual Testing#

Build and start the server in one terminal:

cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build

./build/rocm-ernic --socket /tmp/test.sock

Run the test client in another terminal:

./build/tests/test_pci_client --socket /tmp/test.sock

CTest#

Run all registered tests via CTest:

ctest --test-dir build

With verbose output on failure:

ctest --test-dir build --output-on-failure

To run the tests under valgrind’s memcheck, as the Build and Test workflow’s GCC Debug leg does, use a GCC build without the sanitizers, configured with valgrind installed and with -DERNIC_TRIVIAL_AUTO_VAR_INIT=OFF, since a build that fills uninitialized locals hides the reads of them memcheck reports. Leave out the tests that start the server or run a script, which valgrind would only check the script for:

cmake -B build -G Ninja -DERNIC_TRIVIAL_AUTO_VAR_INIT=OFF
cmake --build build
skip='pci-config-test|find-rdma-device-tuple|find-ipv4-gid-index'
skip+='|server-lifecycle|ionic-server-smoke|ionic-ci|tcp-mesh-ci'
skip+='|nvmeof-ci|s3-ci|ionic-stats-interval-cli|ionic-eth-queues-cli'
skip+='|cmake-subproject|ernic-package-deb|ernic-package-deb-config-paths'
skip+='|ernic-vfu-client|ernic-cmb|ernic-ionic-driver|ernic-p4-driver'
skip+='|ernic-ionic-hw-stats|ernic-mesh-stress|ernic-mesh-flow'
skip+='|ernic-mesh-flr'
skip+='|ernic-feature-macros|ernic-boot-guest|ernic-ci-images'
skip+='|ernic-check-guest-image-tag'
opts='--leak-check=full --track-origins=yes --num-callers=40'
opts+=' --error-exitcode=1'
ctest --test-dir build -T memcheck --output-on-failure \
  --overwrite "MemoryCheckCommand=$(command -v valgrind)" \
  --overwrite "MemoryCheckCommandOptions=$opts" \
  -E "^($skip)$"

Each test’s valgrind report is in build/Testing/Temporary/MemoryChecker.<n>.log.

The test scripts that start the server run it under the command in ERNIC_TEST_SERVER_WRAPPER, if that’s set, as does tests/test_loopback_ci.sh. The command is split on whitespace, so no word of it can contain a space. test_server_lifecycle doesn’t read it; run that program under valgrind with --trace-children=yes, which follows it into each server it starts. To run the server under valgrind, as the same leg does, have valgrind write a log for each process, since the scripts don’t all check how the server exited. With opts as above:

srv='pci-config-test|ionic-server-smoke'
srv+='|ionic-ci|tcp-mesh-ci|nvmeof-ci|s3-ci'
srv+='|ernic-vfu-client|ernic-cmb|ernic-ionic-driver|ernic-p4-driver'
srv+='|ernic-ionic-hw-stats|ernic-mesh-flow|ernic-mesh-flr'
srv+='|ionic-stats-interval-cli|ionic-eth-queues-cli'
logs="$PWD/build/valgrind-server"
rm -rf "$logs"
mkdir "$logs"
opts+=" --log-file=$logs/%p.log"
export ERNIC_TEST_SERVER_WRAPPER="valgrind $opts"
ctest --test-dir build --output-on-failure -R "^($srv)$"
valgrind --trace-children=yes $opts build/tests/test_server_lifecycle
grep -L 'ERROR SUMMARY: 0 errors' "$logs"/*.log

The last command lists the logs with a report. ernic-mesh-stress isn’t in the list: it kills nodes with SIGKILL on purpose, so their logs never get a summary. CI runs it under the sanitizers instead.

Multi-VM RDMA Testing#

With two VMs launched via ernicctl, you can run standard RDMA benchmarks over the emulated NICs.

Prerequisites:

  1. One host TAP per instance, all enslaved to a shared bridge, so the guests can reach each other over IP (see The ionic Device):

    sudo ip link add ernicbr0 type bridge
sudo ip link set ernicbr0 up
for n in 1 2; do
  sudo ip tuntap add dev "ernic-tap${n}" mode tap \
    user "$USER"
  sudo ip link set "ernic-tap${n}" master ernicbr0 up
done

    The ernic_host_setup Ansible role does this for you.

  2. Start the rocm-ernic service and launch two VMs (see systemd Service and ernicctl).

  3. Provision both guests with the ionic driver, built by DKMS, and an rdma-core with the ionic provider, which the CI guest image already has. The guest-setup play does both (see Ansible-Based Testing), and ernicctl driver-push --install the driver alone.

  4. Give the emulated NICs IP addresses in both VMs, as Ethernet Connectivity shows, unless the guest-setup play has, which gives instance 1 192.168.200.10, instance 2 192.168.200.20, and so on. With its udev rules (udev/99-rocm-ernic.rules) the interface is rocm-ernic0; without them it has a name from its PCI address, such as enp1s0.

  5. In each VM, find the RDMA device’s name, which the examples below pass as $DEV, and the index of the IPv4-mapped GID (::ffff:a.b.c.d) for its address, which they pass as $GID. The name is rocm-rdma-ernic0 with the udev rules, and one such as rocep1s0 without them. The GID index is often 1, but it isn’t fixed, and the two VMs can differ. scripts/find-rdma-device.sh and scripts/find-ipv4-gid-index.sh look them up; run them in each guest, the second with the device and that guest’s own address, for example from the host:

    DEV=$(ssh vm1 'sh -s' < scripts/find-rdma-device.sh)
GID=$(ssh vm1 "sh -s -- $DEV 192.168.200.10" \
  < scripts/find-ipv4-gid-index.sh)

ibv_rc_pingpong#

Latency test using RC (Reliable Connection) QPs:

# VM 1 (server):
ibv_rc_pingpong -d "$DEV" -g "$GID" -n 100

# VM 2 (client), reaching the server over IP to swap
# connection details:
ibv_rc_pingpong -d "$DEV" -g "$GID" -n 100 192.168.200.10

Expected output (TCP mesh backend):

40960 bytes in 0.37 seconds = 0.89 Mbit/sec
5 iters in 0.37 seconds = 73960.40 usec/iter

ib_send_bw#

Bandwidth test using the perftest suite:

# VM 1 (server):
ib_send_bw -d "$DEV" -x "$GID" -n 10 --report_gbits

# VM 2 (client):
ib_send_bw -d "$DEV" -x "$GID" -n 10 --report_gbits \
  192.168.200.10

Expected output:

#bytes  #iterations  BW peak[Gb/sec]  BW average[Gb/sec]
65536   10           0.79             0.12

Ethernet Connectivity#

The emulated NICs carry IP over Ethernet through their host TAPs and the bridge joining them; the TCP mesh carries only RDMA. Ping between VMs:

# VM 1:
sudo ip link set rocm-ernic0 up
sudo ip addr add 192.168.200.10/24 dev rocm-ernic0

# VM 2:
sudo ip link set rocm-ernic0 up
sudo ip addr add 192.168.200.20/24 dev rocm-ernic0

# From VM 1:
ping 192.168.200.20

Ansible-Based Testing#

The ansible/ directory contains playbooks that automate the multi-VM test workflow: building the server, installing the systemd service, provisioning already-running guests with the driver and the ionic rdma-core provider, and running iperf3, perftest, RDMA-Tutorial and NVMe-oF tests against them. The guest disk is not built here; see The guest image.

Prerequisites#

  • ansible-core 2.18+, which is what community.general 13 needs. Ubuntu 24.04’s ansible package ships 2.16; use pipx install ansible-core or the Ansible PPA.

  • The community.general Galaxy collection, which is all requirements.yml resolves to

cd ansible
ansible-galaxy collection install \
  -r requirements.yml

Running the full workflow#

The guests must be up and running before you start. site.yml provisions and tests VMs; it never creates them, and every play after the first one fails without them.

It is not quite a single command, because of the order the phases impose. Phase 1 installs the service that launches the guests, so it has to run before there are any; and it also stops whatever is running, unless ernic_restart_existing is false. Launching the VMs and then running site.yml plain therefore tears down the guests the run needs, and vm-register fails with no VM attached to any instance.

Fetch the published guest image once with scripts/fetch-guest-image.sh (see The guest image below), then:

cd ansible

# 1. Build, install the service and ernicctl.  Run the
#    play, not site.yml --tags host-setup: site.yml always
#    registers the VMs, and there are none yet.
ansible-playbook playbooks/host-setup.yml

# 2. Attach a VM to each instance.
sudo ernicctl vm-launch 1

# 3. Provision the guests and run the tests, leaving
#    the VMs from step 2 alone.
ansible-playbook site.yml -e ernic_restart_existing=false

On later runs, steps 1 and 3 collapse back into the single ansible-playbook site.yml -e ernic_restart_existing=false for as long as the guests stay up. Dropping the override is what you want when you do mean to recycle the mesh — it stops the VMs and restarts the service, after which step 2 has to be repeated.

The CI lanes launch their own VMs and drive them with ci-site.yml, which imports no host-setup play and so neither tears them down nor touches the systemd service.

site.yml runs seven plays in order:

  1. host-setup – builds the project, installs the service and ernicctl, templates the env file, and starts the service.

  2. vm-register – reads the launcher’s instances.json and adds each running VM to the ernic_vms group with its SSH port, user and NIC address. Everything below depends on it.

  3. guest-setup – installs the ionic rdma-core provider when the image does not already carry a matching one, builds and loads the guest driver from the ionic DKMS package, and assigns IPs to the emulated NICs.

  4. sanity-tests – runs iperf3 between two VMs for TCP/IP validation and ib_send_bw / ibv_rc_pingpong for RDMA verification.

  5. tutorial-tests – builds examples from the RDMA-Tutorial and runs each between the two VMs; see RDMA-Tutorial examples.

  6. tcp-performance-tests – the iperf3 sweep.

  7. performance-tests – the RDMA perftest sweep.

The setup plays are thin wrappers around the roles of the rocm.ernic collection, whose source lives in ansible/roles/; see The rocm.ernic Ansible collection below.

Running individual plays#

Each play can also be run separately. guest-setup, nvmeof-tests, nvmeof-kv-tests and s3-tests run on the ernic_vms group, which only vm-register fills, and only for the rest of the ansible-playbook run that called it, so those run behind it in the same command; on their own they find no hosts and do nothing:

ansible-playbook playbooks/host-setup.yml
ansible-playbook playbooks/vm-register.yml playbooks/guest-setup.yml
ansible-playbook playbooks/sanity-tests.yml
ansible-playbook playbooks/tutorial-tests.yml
ansible-playbook playbooks/vm-register.yml playbooks/nvmeof-tests.yml
ansible-playbook playbooks/vm-register.yml \
  playbooks/nvmeof-kv-tests.yml
ansible-playbook playbooks/vm-register.yml playbooks/s3-tests.yml
ansible-playbook playbooks/tcp-performance-tests.yml
ansible-playbook playbooks/performance-tests.yml

ci-site.yml runs them the same way, behind vm-register, selected by tag, as NVMe-oF Controller shows.

Variable overrides#

Override any default from group_vars/all.yml with -e:

# Four instances instead of two
ansible-playbook site.yml -e ernic_instances=4

# Skip the build (use existing install)
ansible-playbook site.yml -e ernic_build=false

# Skip sanity tests
ansible-playbook site.yml -e ernic_tests=false

# Pin a different published image
ansible-playbook site.yml \
  -e ernic_vm_artifact_tag=<tag>

# Use a backing image you staged yourself
ansible-playbook site.yml \
  -e ernic_vm_backing=/path/to/backing.qcow2

group_vars/all.yml holds the site configuration for this repo; the per-role defaults live in each role’s defaults/main.yml under the collection described below. Anything set in group_vars/all.yml wins over a role default. See ansible/PLAYBOOKS.md for additional usage notes.

RDMA-Tutorial examples#

playbooks/tutorial-tests.yml runs examples from RDMA-Tutorial, a short introduction to programming with verbs, to check that code written the way it teaches works over rocm-ernic. It covers example 1 (RC send/recv) and example 2 (RC RDMA write), with the server in VM 1 and the client in VM 2.

The tutorial keeps each example as a commit, and they address the peer by InfiniBand LID. The play pins each example to its commit and applies a patch from ansible/playbooks/files/rdma-tutorial/ that exchanges the peers’ IPv4-mapped GIDs instead, as RoCE needs, and uses the port’s active MTU. It also sets SO_REUSEADDR on the server’s socket, so a rerun can bind the same port while the last run’s connection is still in TIME_WAIT. The controller clones the tutorial and applies the patches, and copies the result into the guests, which build it, so they need neither network access nor git. As with perftest, the IPv4-mapped GID reaches a peer only if its instance advertises the guest’s IPv4 address (ERNIC_GUEST_GIDS_<n>, or ernic_guest_gids in the host-setup role), as both CI lanes do.

An example passes when the client and the server both exit 0 and each has logged its throughput, which it does only after its last operation. Upstream runs 5 or 10 million operations, which take tens of minutes over the emulated NIC; ernic_rdma_tutorial_ops (default 10000) sets the count. ernic_rdma_tutorial_timeout bounds each process and ernic_rdma_tutorial_port picks the ports they connect on.

The two-VM job in system-tests.yml runs it after the sanity play.

The guest image#

Nothing in ansible/ builds a guest image. The guests boot the CI guest image, defined in ci/images/guest/ and published to GHCR as an OCI artifact (see CI images): mainline kernel 7.2.6 on Ubuntu 26.04 (resolute), with the RDMA userspace, the DKMS toolchain, perftest and a distro rdma-core 61.0 carrying the ionic provider.

The image has no password and no SSH key. Whatever boots it authorizes a key through a NoCloud seed, for the ubuntu account, which keeps its passwordless sudo: ci/boot-guest.sh makes one for each boot, and ernicctl vm-launch, which runs it, also authorizes ERNIC_VM_SSH_IDENTITY’s public key, or by default that of the first of id_rsa, id_ed25519 and id_ecdsa in the ~/.ssh of the user running it with sudo. So you log in, and the plays here connect, with your own key; host setup fails early, saying how to make one, if you have none. Each boot is a new cloud-init instance, so the guest makes host keys of its own.

scripts/fetch-guest-image.sh --dest DIR pulls the image ci/guest-image.env pins and its vm-info.json metadata with oras, decompresses the qcow2 and runs qemu-img check over it. The download is skipped when the tag is already unpacked. It lands the same bytes in the same layout as .github/actions/fetch-guest-vm, which the hosted jobs use.

It also checks the image’s vm-info.json against this checkout and refuses the image when they disagree. That happens between the metadata pull and the disk pull, so a rejection costs kilobytes rather than the 1.6 GB it would cost after – and every assertion reads either the metadata or a file in this checkout, so pulling the disk first could not change the verdict anyway. Verification reruns on the cached path too, because repinning IONIC_KERNEL_REF invalidates a directory that was correct when it was pulled. --no-verify skips the lot.

The kernel floor it enforces is two-sided. drivers/infiniband/hw/ionic merged in 6.18, which ernic_ionic_min_kernel also asserts against the running guest; and ionic-ernic calls ib_umem_get_va, which landed after 7.0, so a 7.0 guest clears the floor and then fails the DKMS build. The script compares the image kernel’s major.minor against IONIC_KERNEL_REF in cmake/ErnicKernelModule.cmake – as does ernic_guest_setup, against the kernel the guest actually booted, before it starts that build.

The CI guest kernel badge in README.md has to be hardcoded – shields.io cannot read the image – so without a check a tag bump would leave the front page advertising a kernel nothing ships. Two independent implementations compare them: the fetch script, on the manual path, and an inline copy in the Read VM info step of the loopback job in .github/workflows/system-tests.yml, on every pull request. The hosted jobs pull through .github/actions/fetch-guest-vm, not this script, so neither copy is redundant.

Four more properties are site expectations rather than repo-derivable facts, so the caller supplies them: --expect-user, --expect-disk, --expect-release and --expect-flavour. --expect-flavour ionic is what catches a gpu-flavour image reaching roles that want the ionic userspace. These assertions used to live in playbooks/vm-fetch.yml, which 0.2.0 removed; in the script they cover every caller, not just the one that ran a play.

ernic_vm_artifact_tag defaults to GUEST_ARTIFACT_TAG in ci/guest-image.env, the pin the CI lanes read, so the VMs launched here are the VMs CI tests unless you override it.

The pinned image is flavour ionic and carries no ROCm, so ernic_gpu_passthrough defaults off alongside it. A GPU rig needs a GPU-flavoured image.

The rocm.ernic Ansible collection#

The reusable parts of the automation are packaged as the rocm.ernic Ansible collection, so any suitable guest can be turned into a rocm-ernic RDMA node without the playbooks here:

ernic_guest_setup

Installs the DKMS driver, installs rdma-core with the ionic provider (building it only when the guest’s doesn’t match), applies the udev rules, addresses the emulated NIC and builds rocm-xio.

ernic_host_setup

Builds, installs and starts the rocm-ernic service, binds GPUs to vfio-pci and stages rocm-xio for the guests.

ernic_source

Resolves the rocm-ernic checkout the others copy from, cloning it on the controller when ernic_source_dir is not set.

ernic_srq_dkms, ernic_srq_provider

Build the kernel and userspace halves of shared receive queue support from the patch series in ansible/files/patches/srq/ and rdma-core/: the ionic modules as a DKMS package (by default only checking that they compile), and rdma-core’s ionic provider.

ernic_p4_dkms

Builds and loads ernic_p4.ko, which gives a guest program the P4 engine’s control surface (see P4 Match-Action Engine).

The collection is not published to Ansible Galaxy. Consumers outside this repo install it from a pinned commit, matching the server they run, and address the roles by their fully qualified name:

ansible-galaxy collection install \
  git+https://github.com/ROCm/rocm-ernic.git#/ansible/,<SHA>

roles:
  - role: rocm.ernic.ernic_guest_setup

Playbooks in this repo instead reach the same roles by short name through roles_path in ansible/ansible.cfg, so they always run against this checkout rather than an installed copy. Because that path is relative, run ansible-playbook from the ansible/ directory.

Guest Driver CI#

.github/workflows/driver-build.yml covers the guest driver. Its ionic-patches job reads IONIC_KERNEL_REF straight out of cmake/ErnicKernelModule.cmake, sparse-clones the two ionic subtrees at that ref, and applies every ansible/files/patches/*.patch with git am, failing the pull request if one no longer applies. The ionic modules themselves are not built there: they need headers matching IONIC_KERNEL_REF — the sources track IB-core helpers that move between minor releases, so the guest kernel’s major.minor must equal the ref’s, and no hosted runner carries such a kernel.

.github/workflows/system-tests.yml runs its jobs in the CI builder image, ghcr.io/rocm/rocm-ernic/ci-builder, defined in ci/images/builder/. It first calls ci-images.yml, which publishes the image if this tree’s definition of it isn’t published yet, so a pull request that changes the builder runs every lane in the new image; see CI images.

The workflow boots guests under KVM on hosted runners with ci/boot-guest.sh, as ernicctl vm-launch does, so the vfio-user device sits behind a PCIe root port and SSH is forwarded from 127.0.0.1 only. The guest image has no key of its own; the helper authorizes one made for the job. The workflow provisions the guests by running the collection itself — ansible-playbook ci-site.yml --tags guest-setup against a generated instances.json — rather than by copying sources in over ssh. The role is therefore exercised on every pull request, and the guest build in CI is the same one a site.yml run produces. The workflow installs only kernel headers and the build toolchain before handing over; the mainline kernel itself must already be in the guest image, and ernic_guest_setup asserts that it matches the pinned ref before it starts the DKMS build.

CI images#

The images CI runs in are defined under ci/images/ and published to GHCR as ghcr.io/rocm/rocm-ernic/NAME, with the workflow’s GITHUB_TOKEN:

ci-builder

The container the VM lanes run in, defined in ci/images/builder/: QEMU with the vfio-user client, libvfio-user, and the tools to boot, provision and fetch a guest.

guest-ionic

The guest disk the lanes boot, defined in ci/images/guest/ and published as an OCI artifact: the zstd-compressed qcow2, with its vm-info.json attached. build.sh builds it in the builder, with KVM: Ubuntu’s cloud image boots once while cloud-init installs packages/ionic.txt, then it gets the mainline kernel, provision/ionic.sh, a trim to that one kernel, and checks/ionic.sh. Last, it’s sealed: the build’s key and the host keys are removed, the password is locked, and cloud-init is reset, so the next boot is a new instance that takes its key from a seed (see The guest image).

The packages are public, so pulling needs no credentials.

An image’s tag names its contents: a readable prefix from its pins, then 12 hex digits of a SHA-256 over every file defining it. ci/images/image-tag.sh NAME prints it. A tag, once published, isn’t built or pushed again, so it always names one build, and develop runs exactly what the pull request that changed the image tested.

ci/guest-image.env is the lockfile. It pins the builder as BUILDER_IMAGE and BUILDER_TAG, and the lanes’ container: image: lines name it in full, because the security scan can’t tell that an image named by an expression is pinned. It pins the guest as GUEST_ARTIFACT_REPO and GUEST_ARTIFACT_TAG, with its disk, account and metadata type. After changing an image’s definition, run

ci/images/image-tag.sh --write

and commit the result. Every pull request runs image-tag.sh --check, which fails if any pin isn’t the tree’s, or if the guest’s kernel isn’t IONIC_KERNEL_REF, and tools/check-guest-image-tag.sh, which fails if a tag appears anywhere else (the Image pins workflow).

ci-images.yml, which system-tests.yml calls before its lanes, publishes an image whose tag the registry hasn’t got, with ci/images/ensure-image.sh. That builds it, runs the image’s check.sh, and pushes it only if it passes. The builder’s check runs inside it; the guest’s boots it with ci/boot-guest.sh, as the lanes do, and checks the seal holds: only the boot’s key logs in, the password is locked, and the guest made its own host keys. So a pull request that changes an image publishes it and runs every lane with it. A pull request from a fork can’t push, so one changing an image fails; a maintainer pushes the branch to ROCm/rocm-ernic instead.

To rebuild an image whose definition hasn’t changed, for Ubuntu’s updates, or the guest’s newer cloud image, bump REBUILD in its pins.env. To build and check the builder locally, with Docker’s buildx or podman, without touching the registry:

ci/images/ensure-image.sh --build-only builder

The guest builds in the builder, with KVM, into build-ci-images/guest/; with rootless podman, TAG being BUILDER_TAG in ci/guest-image.env:

podman run --rm --user root --group-add keep-groups \
  --device /dev/kvm -v "$PWD:/src" -w /src \
  ghcr.io/rocm/rocm-ernic/ci-builder:TAG \
  ci/images/ensure-image.sh --build-only guest

ci/images/README.md says what Docker needs as well.

ci-images-prune.yml deletes the versions nothing needs every Monday, with ci/images/prune-images.sh. It keeps the tags develop’s lockfile pins, the 10 newest, and anything under 30 days old, tagged otherwise (such as the registry cache, buildcache), or needed by a version it keeps. A pruned tag that’s wanted again is rebuilt the next time a run needs it. Every run lists what it would delete; only runs on develop delete.

The ernic-ci-images, ernic-check-guest-image-tag and ernic-prune-images tests check these scripts against stand-ins for Docker, oras, gh and the registry. For the details, see ci/images/README.md. Likewise, ernic-boot-guest checks ci/boot-guest.sh, and ernicctl vm-launch and vm-stop through it, against stand-ins for QEMU and ssh, so no guest boots.

Adding New Tests#

  1. Create a test source file in tests/.

  2. Build it in tests/CMakeLists.txt with ernic_add_test_program() (cmake/ErnicTesting.cmake), which gives it the project’s warning, hardening and sanitizer flags and include directories. DEPS names the libraries it links (ibverbs, vfio-user, json-c, pthread) and HEADER_DEPS those whose headers it only includes. Where a family of tests links the same part of src/, use its list from the top of the file (ERNIC_TEST_ADMINQ_SOURCES, for one).

  3. Register a test that runs the program on its own with ernic_add_unit_test(), giving its timeout. A test that needs a script around the program, such as one that starts the server, uses add_test().

Examples:

ernic_add_test_program(ernic-test-new-feature
    SOURCES
        test_new_feature.c
        ${ERNIC_TEST_ADMINQ_SOURCES}
    HEADER_DEPS vfio-user ibverbs
)
ernic_add_unit_test(new-feature-unit ernic-test-new-feature
    TIMEOUT 30)

ernic_add_test_program(test_new_client
    SOURCES test_new_client.c
)
add_test(
    NAME new-client-test
    COMMAND ${CMAKE_CURRENT_SOURCE_DIR}/run-test.sh
        $<TARGET_FILE:test_new_client>
        $<TARGET_FILE:rocm-ernic>
)
set_tests_properties(new-client-test PROPERTIES
    TIMEOUT 30
    RUN_SERIAL TRUE
)
