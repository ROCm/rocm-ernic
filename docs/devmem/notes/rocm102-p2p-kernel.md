## 4. The KFD eviction finding (`K/scripts/hip-loop.sh`, `E/hip-loop/SUMMARY.txt`)

On the stock kernel a devmem bind pins the `hipMalloc` buffer to GTT, which evicts and restores
the KFD process (`evicted_ms` 102 to 107), and HIP's next device-to-host copy returns nothing
or hangs (`rocm102-gpu.md` F1).

**On `7.2.6-devmemp2p`: absent in 24 of 24 iterations** (18 `hipMemcpy` fills, 6 GPU-kernel
fills; each: `hipMalloc` 4 MiB, fill, export, bind, send 3 s, three readbacks over 5 s, rewrite
through HIP, readback).

| Measure | 24 iterations |
| --- | --- |
| Receiver verdict | 24 PASS, 17847435407 bytes verified, 0 mismatches |
| KFD `evicted_ms` while bound | 0 in 24 |
| Placement while bound (`amdgpu_vm_info`) | `VRAM VISIBLE pin count 1` in 24 |
| Frag addresses | 4696299 in GPU BAR0, 0 in System RAM |
| HIP readbacks after the bind equal to what was written | 4 of 4 in 24 (96 of 96); 0 `DIFFERS` lines, 0 hangs |

Together with the other runs on this kernel, every `hipMalloc` case behaved the same: V3, V4,
V6, six large-buffer cases, S2 (330 s), W1, W2, 30 in the leak loop, the final check: 67 cases,
`evicted_ms` 0 wherever it was captured, no readback difference, no hang.

**Why:** with the dynamic peer-to-peer attachment amdgpu pins the buffer where it is (pin mask
0x6 allows VRAM), so nothing moves and the KFD process is never evicted. The defect behind the
stock-kernel symptom (a KFD evict/restore cycle on this emulated GPU breaking the next
device-to-host copy) is still there; this kernel no longer triggers it through a devmem bind.
`amdgpu_evict_vram` was NOT RUN on this kernel.

## 5. `--rocm-rdma-mode vram`: unchanged, and why

Same result as on the stock kernel, twice: `Couldn't allocate MR with error=14` on both sides,
reported by quick-start as the known limitation.

Traced this time (`K/scripts/rdma-vram-traced.sh`, `umem.bt`; `E/rdma-vram/*-umem-r102-N.txt`,
the same in both guests):

    ib_write_bw ionic_reg_user_mr(start=0x738463a00000, length=67305544)
    ib_write_bw   check_vma_flags(vma 0x738463a00000-0x738467c00000 vm_flags=0xc0644fb VM_IO=1 VM_PFNMAP=1, gup_flags=0x290101)
    ib_write_bw   check_vma_flags returned -14
    ib_write_bw   __gup_longterm_locked returned -14
    ib_write_bw   pin_user_pages_fast returned -14
    ib_write_bw ionic_reg_user_mr returned -14

- This mode registers the `hipMalloc` **address** (`ibv_reg_mr`), so the kernel must pin user
  pages: `ib_umem_get_va()` -> `pin_user_pages_fast(FOLL_LONGTERM)` (`drivers/infiniband/core/umem.c:240`).
- The address is a mapping of `/dev/dri/renderD128` with `VmFlags: ... pf io ...`
  (`VM_PFNMAP | VM_IO`; printed by `hip_devmem_src2` for every HIP case). VRAM has no
  `struct page` a GUP caller may hold.
- `mm/gup.c:1207`: `if (vm_flags & (VM_IO | VM_PFNMAP)) return -EFAULT;`. EFAULT is 14.
- The backport changes only `net/core/devmem.c`. It cannot affect this path, and no devmem or
  dma-buf change would: the fix is to register the buffer as a dma-buf, which is the `dmabuf`
  mode, and that passes on both kernels (and on this one the control `ib_send_bw` in the same
  trace pins 32 ordinary pages successfully).

## 8. Findings

- **F1. A VRAM request that does not fit is satisfied from GTT without a word.** A 1024 MiB GEM
  BO asked for in `AMDGPU_GEM_DOMAIN_VRAM` (1021 MiB free) is created, bound and sent from
  system RAM (`GTT pin count 1`, 659500 System RAM frags); 1020 MiB stays in VRAM. Payload
  correct either way. amdgpu behaviour, not devmem; a test that must prove VRAM placement has
  to look at the addresses, as these do.
- **F2. `hipMalloc` of 1016 MiB fails (`out of memory`) where a 1016 MiB GEM BO succeeds**;
  960 MiB works. HIP's own limit, reached before any bind. The exact threshold was not searched.
- **F3. `bindeb-pkg` drops make-variable toolchain choices** (`RUSTC=`), so a faithful
  `CONFIG_RUST=y` build needs the Rust toolchain on `PATH`. Cost one 40 s failed build.
- **F4. The image's `sdxi_char` cannot be rebuilt from the image**: no source in the guest, no
  DKMS package. Anyone changing the kernel needs rocm-systems at `/etc/sdxi-guest-ref`.
- **F5. Receiver-side Rx loss under sustained load persists** (1601 frames in M10; 3085 by the
  end), same signature as `rocm102-devmem.md` F3. Not caused by this kernel; every byte verified.
- **Harness:** `hip-loop.sh`'s first summary printed 0 in the bytes column (greedy regex took
  `mismatch_zero_bytes`); fixed and regenerated from the same evidence files. The first copy of
  the runner made with `sed` was empty; rewritten by hand before any case ran.
